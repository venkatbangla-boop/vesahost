# VESA 360 - Scope, Change Control, Decision Rights and Privacy

## Approved current personal-demo purpose

The owner has stated that the current VESA 360 program is for **personal, non-commercial development and demonstrations**, not a paid commercial SaaS, subscription or live buyer/factory multi-tenant production system. Do not repeatedly block proposed demo-only frontend development merely because garment/business terminology appears in a description. Public hosting suitability depends on actual website content/use and current GitHub Pages rules, however; check those facts at a real release boundary, not on every local calculation patch.

This package adds no service, deployment, DNS change or real data. Browser-only login is NOT secure server-side access; anyone may retrieve public static source/JavaScript from a published site. Use synthetic/anonymized data for publicly distributed demos.

## Fixed technical limits

- One GitHub Free repository and local VS Code Codex project. No added AWS/Azure/GCP/Firebase/Supabase/VPS, external authentication, paid provider, cloud database or hosted API.
- JavaScript domain engines compute locally, saved copies and reports generated locally, records in current app's isolated browser storage.
- Manual approved local saved-copy transfer across apps, never realtime sync or remote read/write.
- Preserve the existing VESA shell, EN/BN/HI/TA and home/file/edit/view/tools/help order.
- Keep existing TNA/PPM/AQL calculations, decisions, sampling/Ac-Re, 168 PPM checkpoints, format versions and accepted history unchanged.
- Costing 360 is a separate handover, outside this 15-app count. Do not blend Costing logic into the Supplier Comparison or Commission engines.

## Domain decision authority

- User/business owner chooses app priority, actual business policy, buyer terms and release destination.
- Engineer/Codex may select validated software implementation details within an agreed scope, run tests and collect synthetic screenshots, but may not fabricate missing rates, sample decisions, certificates, LC terms, buyer policies or customer data.
- Buyer approval, bank transaction, statutory compliance and factory inspection require source evidence; developer-admin login or synthetic fixtures do not confer those authorities.
- When one input/policy is missing, gate only dependent computation. Build the remaining safe technical work and note exact unknown.

## Architectural change request protocol

1. Identify need: already owned by existing app? If yes, propose an improvement there, not a second app/master.
2. Record new ownership with fields and a source-of-truth matrix amendment.
3. Map exact files and dependencies; perform real file-level repo audit.
4. Obtain explicit approval for destructive or cross-domain changes; never infer it from the blueprint.
5. Implement one reversible patch group; verify against accepted baseline.
6. Record drift, decisions, tests, rollback and next safe step; only mark true accepted gates.

## Smallest possible integration

- New app code under its app folder first.
- App Centre descriptor and four language open labels added last, after route and tests exist.
- Shared shell/CSS only change when a demonstrated platform bug requires one platform-owned patch, with full sibling regression.
- No background job, remote notification, payment processing or cloud service for this personal-demo plan.

## Real data and intellectual property

- No real factory/buyer PO, quote, tech pack, artwork, email address, personal contact, contract, credentials or signatures in public Git fixtures, ZIP examples or browser demo seed.
- Real proprietary uploaded files, if any, must remain user-controlled and outside git history; never ingest them into App Centre demo output.
- The `templates/vesa-next-app/` starter is an example, not proof of any new application's functionality.
- Where monetary values are uncertain, set `null` plus source-needed, not `0` unless a genuine measured zero.

## Portfolio review cadence

Review priorities after each complete wave. Do not block unrelated apps waiting on one unavailable buyer/legal/physical acceptance; maintain a `NEEDS_APPROVED_POLICY` exception. Do not automatically start all 15 apps or create all 15 feature branches. Keep development safely bounded and recoverable.
